# Plan: DocuSeal HTML MCP Bridge for LibreChat

Status: IMPLEMENTED — deterministic and local MCP verification pass; live DocuSeal/LibreChat acceptance remains blocked by unavailable deployment prerequisites
Created: 2026-09-29
Scope note: this plan supersedes the previous minimal `server.py` bridge turn; it treats the existing four files as the starting point to be revised, not replaced wholesale.

## 1. Goal

LibreChat users should be able to say, in natural language, something like
"Create a signing template for an NDA with a name field, a date field, and a signature block,"
and have LibreChat:

1. Read the template specification from the conversation.
2. Call MCP tools on this bridge to create the DocuSeal template (HTML → PDF template).
3. Receive back the created template's identity and details (name, ID, field schema, creation timestamp).
4. Optionally search / retrieve / load that template again later (e.g., before sending a submission).

The bridge must therefore be usable as a **LibreChat MCP client target** first, and as a sensible **DocuSeal REST wrapper** second.

## 3. Requirements

### Functional
- F1. LibreChat connects to the bridge over Streamable HTTP at `http://<reachable-bridge-host>:8000/mcp`; this is the only front-end MCP transport in scope.
- F2. Given a natural-language template specification, LibreChat generates HTML with DocuSeal field tags and calls `create_template_from_html`; the bridge posts that HTML to `POST /api/v1/templates/html` and returns the created template identity/details.
- F3. Creation and retrieval expose verified template ID, name, fields, slug, and timestamps when returned by DocuSeal.
- F4. Search uses `GET /api/v1/templates`; load/retrieve by ID uses the documented `GET /api/v1/templates/{id}` detail route.
- F5. Submission creation uses `POST /api/v1/submissions`; status-by-ID uses the documented `GET /api/v1/submissions/{id}` route; listing/filtering uses the required `GET /api/v1/submissions` route. Live signing requests require explicit authorization.

### Non-functional
- N1. No hardcoded secrets; `DOCUSEAL_API_KEY` stays in bridge server configuration and is never sent to LibreChat or exposed in tool output.
- N2. Validate DocuSeal responses at the boundary; tolerate documented optional/unknown fields without fabricating values.
- N3. Errors surface as readable tool errors without leaking credentials, request secrets, or document contents.
- N4. Keep bridge network exposure/authentication separate from bridge-to-DocuSeal API authentication; determine and document the bridge access boundary before deployment.

## 4. Tool Contract (target shape, gated on DocuSeal evidence)

LibreChat receives the user's natural-language requirements, constructs complete HTML using the documented DocuSeal tags, and calls `create_template_from_html(template_name, html_content, document_size="Letter")`. Keep template rendering in the model; the bridge is a REST-backed MCP adapter, not a second HTML/template-generation engine.

- The tool description/server instructions must tell the model to produce valid HTML with DocuSeal elements such as `<text-field>`, `<date-field>`, and `<signature-field>`, each named and assigned a signer role; style dimensions control field size/position.
- The bridge sends `{"name": template_name, "html": html_content, "size": document_size}` to `POST /api/v1/templates/html` and returns the created template's verified identity and field schema.
- Add a `get_template(template_id)` MCP tool to load a template's details after creation. Keep `search_templates(query)` for later discovery.
- Use normal MCP tool success/error results; do not add a uniform `{ok, error}` envelope unless LibreChat integration demonstrates it is needed.
- The HTML tags are generated by the model from the tool instructions; do not rewrite user HTML in the bridge. Failures from DocuSeal must be returned as readable MCP tool errors with secrets omitted.

## 5. REST / Endpoint Contract Validation

- Preserve the required routes `GET /api/v1/templates`, `POST /api/v1/templates/html`, `POST /api/v1/submissions`, and `GET /api/v1/submissions`.
- DocuSeal's official API documents the HTML request properties `html`, `name`, and `size`; the returned template example includes `id`, `slug`, `name`, `fields`, `submitters`, `created_at`, and `documents`. The published route omits `/api/v1`; this bridge retains the user's required `/api/v1` prefix for their on-prem target. Validate the prefix against that target before live calls.
- Template list supports `q`, `limit` (default 10, maximum 100), and returns `{data, pagination}` with template fields. The published detail route is `GET /templates/{id}`; use `/api/v1/templates/{id}` for the bridge's load tool.
- Submission list supports `template_id`, `status`, `q`, and pagination; it returns `{data, pagination}`. Submission detail is documented as `GET /submissions/{id}`; use `/api/v1/submissions/{id}` for status by ID.
- HTML guide documents custom elements including `text-field`, `signature-field`, `date-field`, `image-field`, `initials-field`, `phone-field`, `stamp-field`, `file-field`, `checkbox-field`, `radio-field`, `select-field`, `multi-select-field`, `payment-field`, and `verification-field`. Common field attributes include `name`, `role`, `required`, and CSS `style`.
- Do not connect to DocuSeal `/mcp`; server-to-upstream communication remains REST-only.


## Verified Findings (2026-09-29)

- LibreChat documentation supports remote Streamable HTTP MCP with `type: streamable-http`, `url`, optional `timeout`, headers, and server instructions. Source: https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/mcp_servers
- LibreChat overview uses the same streamable-http configuration and requires restart for manual YAML changes. Source: https://www.librechat.ai/docs/features/mcp
- MCP Python SDK tag v1.16.0 defines supported protocol versions `2024-11-05`, `2025-03-26`, and latest `2025-06-18`; its server initialization echoes a requested supported version. Source: https://github.com/modelcontextprotocol/python-sdk/blob/v1.16.0/src/mcp/shared/version.py and https://github.com/modelcontextprotocol/python-sdk/blob/v1.16.0/src/mcp/server/session.py
- SDK v1.16.0 FastMCP `run()` accepts `stdio`, `sse`, or `streamable-http`, uses host/port/path via constructor settings, defaults streamable endpoint to `/mcp`, and exposes `sse_app()` and `streamable_http_app()`. Source: https://github.com/modelcontextprotocol/python-sdk/blob/v1.16.0/src/mcp/server/fastmcp/server.py
- DocuSeal's published REST reference documents `/templates/html`, `/templates`, `/templates/{id}`, `/submissions`, and `/submissions/{id}` with the body/query/response details above. This repo must retain the user's `/api/v1` prefix; its target instance is not yet live-verified. Source: https://www.docuseal.com/docs/api
- DocuSeal HTML tags and attributes are documented at https://www.docuseal.com/guides/create-pdf-document-fillable-form-with-html-api

- Implementation verification: `.venv/bin/python -m pytest -q` — 42 passed; 98.20% combined source-line coverage (`docuseal_api.py` 99%, `server.py` 94%); one non-blocking Pydantic SDK warning about an unresolved `lifespan` annotation.
- Live local MCP smoke: server started on loopback; SDK client initialized Streamable HTTP at `/mcp`, negotiated `2025-06-18`, and discovered all six tools. Mock-backed integration exercised all six tools and the required REST routes.
- Docker build/config verification was unavailable because the Docker daemon was not running. Compose now requires the name of an existing private Docker network shared with LibreChat and publishes no host port.
